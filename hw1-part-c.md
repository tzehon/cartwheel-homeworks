# HW1 Part C: account-change and dispute escalation

## Recorded failures

`SPEC.md` requires human escalation for account changes (ESC-2) and disputes
(ESC-3). The original system prompt only described escalation when the agent
was unsure or an action exceeded its authority. Its refusal of "credential
changes" also made the account-change boundary ambiguous.

The existing conversations provide the before evidence:

- JSONL line 7: shopper user 1 requested an email change. The agent refused
  without calling a tool.
- JSONL line 10: support user 9501 requested a dispute for order 4127. The
  order lookup succeeded, but the agent offered a refund instead of escalating.
  No refund was issued.

The escalation tool was available to both roles. These observations support a
model-instruction change rather than a change to authorization or tool logic.

## Minimal prompt revision

In `SYSTEM_PROMPT_TEMPLATE` in `agent/agent.py`, narrow the refusal wording from
"payment-card or credential changes" to "payment-card changes or
payment-credential handling", matching SCOPE-2. Add these sentences under
Escalation:

> Always call escalate_to_human for account changes (including email changes)
> and disputes. Do not merely refuse account changes or substitute a refund
> for a dispute.

The instructions describe general request categories; they contain no test
address, order identifier, or evaluation input. Tool implementations and
authorization checks are unchanged.

## Observed after results

The assistant reran the exact requests in fresh CLI sessions with `gpt-4o-mini`,
debug output enabled, and tracing disabled. The prompt version changed from
`d108f6949e5e` to `c8b01b1a7fab`.

| Case | Before | After |
| --- | --- | --- |
| Email change, shopper 1 | Refusal; no tool call | `escalate_to_human` returned success; response confirmed human follow-up |
| Dispute, support 9501 | `get_order`, followed by a refund offer | `escalate_to_human` returned success; response confirmed dispute escalation |

The full after responses, arguments, and results are saved on JSONL lines 11
and 12, linked to their before sessions. The original ten records are preserved.

Each live rerun used its own temporary database generated by the course seed.
The relevant users and order 4127 were verified identical to the current course
database before running. Each test created one local escalation (ticket 151 in
each separate copy); neither modified users, orders, or refunds. These are test
tickets in temporary databases, not tickets in the student's main database.

The initial sandboxed model attempt failed with a connection error and produced
no response; it is not included as a completed JSONL conversation. After an
approval-review rejection of the main-database rerun, the isolated fictional-data
